# Research: Hamlet GPUI template architecture

## Summary
Hamlet’s proposal is compatible with GPUI and resembles important ownership patterns in Zed and native frameworks, but it is a **project convention, not a universal GUI architecture**. Adopt feature-local UI and dialogs, purpose-specific shared components, and durable application/workflow ownership; retain the toolkit’s centralized modal presentation machinery without turning it into a registry of every product dialog.

## Scope and provenance
Five representative examples: Zed, GPUI Kit, Qt Quick/QML, SwiftUI, and WPF. Research inspected primary documentation and upstream code on **2026-10-08**. The fetched `main` snapshots were Zed `b47a4ca595d3a3fba116b9e78ef01a46e2e43f3e` and Kit `02daace3522954eb8b3a8db77d59c3bbaa5a839d`. Code links below are immutable snapshots. ## Findings
1. **Claim: GPUI allows non-rendering application state without requiring a framework-independent core.** **Sources:** [GPUI ownership](https://zed.dev/blog/gpui-ownership), [Zed Project](https://github.com/zed-industries/zed/blob/b47a4ca595d3a3fba116b9e78ef01a46e2e43f3e/crates/project/src/project.rs). **Support:** direct evidence. **Confidence:** high.
   GPUI calls models and views “entities”; the framework `App` owns their state, while `Entity<T>` handles govern retention and contextual access. Zed’s `Project` coordinates tasks, language-server and collaboration operations using GPUI entities. **Interpretation:** Hamlet’s application model can itself be a non-rendering GPUI entity; pure Rust logic can be extracted where useful, not as a compulsory purity rule. Logical workflow ownership must not be confused with the framework’s storage ownership.

2. **Claim: Feature-local dialogs can coexist with centralized presentation and a shared modal interface.** **Sources:** [Git UI module declarations](https://github.com/zed-industries/zed/blob/b47a4ca595d3a3fba116b9e78ef01a46e2e43f3e/crates/git_ui/src/git_ui.rs), [CommitModal](https://github.com/zed-industries/zed/blob/b47a4ca595d3a3fba116b9e78ef01a46e2e43f3e/crates/git_ui/src/commit_modal.rs), [Kit 0.7.1 window state](https://github.com/longbridge/gpui-kit/blob/87d10ae5e1299d1be18670a37570c5402f952e34/crates/component/src/root.rs). **Support:** direct evidence. **Confidence:** high.
   Zed declares private `mod commit_modal`; its `CommitModal` implements workspace `ModalView` and opens through `workspace.toggle_modal`. Kit 0.7.1 retains active dialog builders and focus restoration in window-owned `WindowState`, rendering layers after application content. **Interpretation:** centralize overlay stacking, focus, dismissal, and rendering—not necessarily feature form state, submit logic, or dialog source files. “Feature-owned” means semantic ownership; the host may retain presentation handles or closures.

3. **Claim: Purpose-specific shared UI is a supported design, not evidence for an undifferentiated global widgets folder.** **Sources:** [Kit architecture](https://github.com/longbridge/gpui-kit/blob/02daace3522954eb8b3a8db77d59c3bbaa5a839d/docs/ARCHITECTURE.md). **Support:** direct evidence for Kit; interpretation for Hamlet. **Confidence:** high/medium respectively.
   The reference assigns reusable behavior and necessary geometry to base, product visual language to presentation, and distinct Input/Textarea/Editor interfaces to a shared internal engine. **Researcher inference:** keep screen-specific children private until another feature genuinely needs their contract; promote shared interaction or visual policy into named modules. Neither these sources nor GPUI prescribe Hamlet’s folders.

4. **Claim: Durable state above replaceable screens has strong native-framework analogues.** **Sources:** [SwiftUI model data](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app/), [WPF Application](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/app-development/application-management-overview), [Zed AppState](https://github.com/zed-industries/zed/blob/b47a4ca595d3a3fba116b9e78ef01a46e2e43f3e/crates/workspace/src/workspace.rs). **Support:** direct evidence; Hamlet lifetime recommendation is inference. **Confidence:** high/medium.
   Apple demonstrates `@State private var library` in the top-level App, shared through the environment. WPF separates Application lifetime from individual windows. Zed’s globally accessible `AppState` bundles services and session/workspace-store entities. **Researcher inference:** Hamlet should retain its host/model independently of whichever screen is rendered. This does not imply surviving process exit or, without an explicit policy, closing every window.

## Implications for Hamlet
These are **researcher recommendations**, not framework mandates:
- Let `application/` coordinate durable workflows while `session/` and `workspace/` retain explicit ownership of their respective state; avoid duplicating authoritative copies in screens or one oversized application struct.
- Keep transient focus, local form edits, text selection, scroll position, and private child views near their screen/workflow. Keep dialogs there too, presented through Kit’s window host. Hamlet’s authoritative per-channel message drafts and selected channel remain workspace-owned, not screen-owned.
- Preserve `api/`, `storage/`, and runtime seams where useful. Private GitHub CLI and Notion HTTP modules can expose different typed operations. Introduce a common `Connector` trait only when a real consumer needs interchangeable capabilities—not merely because both perform external I/O.
- Define host retention, task cancellation, stale-result rejection after session changes, and subscription teardown explicitly. Moving code into `application/` alone does not guarantee these lifetimes.

## Contradictions and caveats
Zed and Kit **do** centralize modal infrastructure; a proposal banning all shared dialog interfaces or hosts would differ from these examples. That does not justify a global product-dialog registry. Qt recommends backend/UI separation more explicitly than GPUI; SwiftUI supports direct model observation without requiring MVVM. No inspected source establishes a universal connector trait, folder layout, or single application-state monolith.
