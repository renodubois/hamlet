# Server architecture and extension costs

This is an assessment of the current implementation, not a commitment to build these features.

| Change | Boundaries it crosses | Awkward seam / likely refactor |
| --- | --- | --- |
| A new channel type | A versioned migration removes/changes the `channels.type = 'text'` CHECK; `ChannelType` gains an enum variant and DB decoder; channel creation/list DTO schemas change; message routes must reject or specialize non-text channels. | Today `messages::post/history` checks only channel existence, not type. A new type cannot safely reuse this path without a typed channel lookup and feature-specific operations. The bootstrap remains an ordinary text channel; do not make it privileged. Regenerate OpenAPI and update route inventory/HTTP tests. |
| Admission or authorization rule | Public signup currently creates a user and session; login resolves username/password; shared protected Actix scope resolves a bearer identity; channel/message services accept all authenticated users. | No admission state, membership, role, or permission schema exists. A new rule needs migrations and service-level authorization on read **and** write, not just a route guard, while preserving the shared auth scope. The route inventory test catches undocumented route registration, not a missing permission check. Add denial HTTP tests per route and decide whether signup stays public. |
| Cookie authentication and CSRF | Cookie issuance/revocation, session lookup, protected scope, error mapping, browser origin policy, response security, and contract security schemes. | Current explicit bearer headers have no ambient cookie CSRF exposure. If cookies are added, SameSite/Secure/HttpOnly and an anti-CSRF mechanism for unsafe methods must be designed together, including login/logout and any future SSE handshake. Do not simply accept cookies in the current bearer parser or assume CORS solves CSRF. |
| SSE publishing | Message/channel creation operations and the shared concrete `EventHub`; HTTP/event identity and write-cancellation tests. | The protected SSE route, bounded shared hub, and periodic session validation now exist; channel (#66) and message (#67) operations prepare payloads before writing and each own a supervised write-plus-notify task. Message responses/events use the bearer-validated author identity and insertion values, with no fallible post-write lookup. Unexpected write-task failure halts the hub until process restart, including fresh streams, because a canceled database step can commit after an early reconnect. Publishing only after a successful commit avoids phantom events but can lose events if the process dies; **best-effort publishing is not durable**. V1 reconnects fresh and recovers through authoritative reads, not replay. A durable requirement would need an outbox, ordered consumption, and recovery/retention policy. See [LIVE-UPDATES.md](LIVE-UPDATES.md) for framing, bounds, authentication and deployment constraints. |

Other observed seams: SQL in feature services is explicit and small, but joins and SQLite-specific constraint classification are repeated; typed SQLite constraint codes and handwritten SeaORM entity mappings would make schema changes safer. The migration crate is the schema authority. The API inventory and OpenAPI assembly remain two explicit lists because utoipa's Actix integration does not currently collect these `web::resource` registrations; inventory checks and response tests mitigate, but do not remove, that maintenance cost. The server uses a single process/SQLite database; multi-instance delivery and production observability are not implemented.
