## Implemented architecture (#47–#61)

See [ARCHITECTURE.md](ARCHITECTURE.md) for implemented module ownership and rules for adding views and server operations, and [PRESENTATION.md](PRESENTATION.md) for editing locations and semantic controls. The full conversion described by the [approved migration plan](../docs/plans/client-gpui-rearchitecture.md) is implemented; [MIGRATION-61.md](MIGRATION-61.md) records the final contraction, ownership audit and scenario equivalents. The original plan is a separately owned planning artifact; its frozen “not started” status is not current implementation status.

`src/main.rs` is startup only. `views/app_shell.rs::AppShell` composes screens and presents session/storage status and retries; child views own controls and subscriptions. `session/` owns authentication, restoration, expiry and cleanup; `conversation/` owns session-scoped requests, polling, history and drafts. `api/` owns the bound HTTP clients, `storage/` the ordered provider/configuration worker, `runtime.rs` the shared execution/time bridge, and `theme.rs` colors/icons. Protected operations take no URL/token arguments.


Automated tests use controlled time/HTTP, isolated files/fake providers and disposable loopback rewrite-server databases; building does not launch the desktop client. Do not run native automation or access a real keyring without separate consent.

## #45 Focused polling and outage/recovery demonstration

Start the unchanged rewrite server as described in `server-rewrite/README.md`. Open two clients (`cd client-gpui && cargo run --locked` in separate graphical terminals); sign up/log in as Alice and Bob on the same server. Keep Alice's window focused on **# general**. From Bob's window publish a message (return focus to Alice afterward); it appears in Alice's selected conversation within about 3 seconds of focus. Create a channel as Bob; Alice discovers it within about 15 seconds of focus. If Alice's window is unfocused, background polling pauses; refocus it to reconcile both resources immediately. **Refresh conversation** and **Refresh channels** remain available independently of the schedule. To demonstrate a burst, publish more than 50 messages as Bob before refocusing Alice: catch-up traverses all server cursor pages and keeps Alice's reading position, or use **Jump to latest**.

For an outage, first leave a draft in Alice's composer, stop the server, and click both refresh controls. The connection status reports which read failed; existing channels, history and draft remain visible. Restart the same server/database; keep Alice focused for automatic retry (3/15-second initial retry, exponential backoff up to 60 seconds per resource), or deliberately refresh immediately. Reconciliation fetches missed messages/channels without replaying writes. An uncertain send still requires checking the conversation before manually resending. The status shows when reads recover. `cargo test --locked focused_polls_pause_resume_and_recover_without_losing_draft` uses GPUI's headless window activation and actual controls; `cargo test --locked second_user_activity_is_found_by_focused_polling_against_unchanged_routes` uses two users and real unchanged rewrite routes. These automated checks alone are **not** physical native window verification. A subsequent consented, uinput-driven two-client desktop smoke is recorded in `VERIFY.md`; human keyboard/IME and accessibility checks remain outstanding.

## #44 Saved Linux session (native provider save/restore/delete observed; locked-store check outstanding)

Build with `keyring` 3.0.4's explicit `sync-secret-service` Linux backend (requires development files for libdbus-1 via pkg-config). At runtime, a graphical user session must provide a running session D-Bus and an unlocked, working `org.freedesktop.secrets` provider (for example GNOME Keyring or KWallet). A headless session or a missing/locked provider may prevent saving, reading or deleting credentials. This client does not use the keyring mock backend or persist a plaintext bearer token. The separate `$XDG_CONFIG_HOME/hamlet-gpui/session.json` (or `~/.config/hamlet-gpui/session.json`) contains only the last successful server URL, user ID/name and token expiry, never a password or token. Remote servers still require HTTPS; local loopback HTTP is for local development only.

After login **or signup**, the authenticated shell shows a Secret Service save result; failed storage is explicitly memory-only; a timed-out save is explicitly unconfirmed (it may finish later), so users must not assume it was saved or deleted. On launch the selected saved server is prefilled, and the stored credential must pass `GET /api/v1/me` with matching user identity before conversations open. A timeout leaves it available for **Retry saved-login restoration**; authoritative rejection or known expiry returns to login and requests deletion. Changing servers clears local conversations and schedules deletion of the old selected credential. Logout clears local state immediately, requests deletion and server revocation separately, and displays distinct warnings if either cannot be confirmed. **Retry saved-login deletion** is shown after an unconfirmed deletion. A hung Secret Service worker cannot be forcibly interrupted; later queued deletion is serialized after any in-flight save, and the UI warns instead of claiming deletion.

To manually verify on a real Linux desktop: start the rewrite server, unlock the Secret Service provider, log in or sign up, wait for the explicit saved status, quit and restart the application, confirm `/me` restoration and your original user, then log out and verify the saved item is gone using the provider's credential manager; restart and confirm no automatic restoration. Also test locked provider and disconnected server without treating a timeout as invalidity. Run `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked`, `cargo build --locked` in `client-gpui/`. Automated tests cover controlled storage failure/order/isolation, restoration model and headless status controls, a loopback `/me` bearer/redirect fixture and real unchanged rewrite-server `/me` routes. **Subsequent native result:** a third GPUI client saved, restored after restart, and deleted a disposable user's credential through `ksecretd` on a private D-Bus and wallet; provider contents and server session were checked and a second restart stayed logged out. The ordinary desktop bus had no activatable Secret Service and showed an honest memory-only warning. A real locked/slow wallet is still untested. Details and boundaries: `VERIFY.md`; headless tests alone did not prove this behavior.

## Compose and publish (#43)

Start the unchanged rewrite server following `server-rewrite/README.md`, then run `cargo run --locked` here and log in. Select a text channel, click the **Message to …** composer, type `first`, press **Shift+Enter**, type `second`, then press **Enter** (or use the named **Send message** icon button; its tooltip explains both keys). The server-created message appears once, with its line break intact. Type an unsent draft, switch channels, type another draft, and switch back: each channel retains its own text only until logout/expiry/restart. Other channels remain writable while one channel is sending. The originating composer becomes read-only and its button shows **Sending…** until the bounded write completes; there are no automatic write retries.

To reproduce uncertainty, log in and prepare a draft, then stop the rewrite server *before* clicking Send. The button unlocks and the draft remains with a warning that publication may already have succeeded. Restart the server, select another channel and return to the original: only the selected channel is reconciled through gap-free refresh. Do not resend until you have checked the server history; equal message text is not proof of publication. To exercise the timeout path, block/delay the server response after receiving a POST instead of stopping it; an ambiguous delivery likewise retains the draft. `cargo test --locked stalled_send_times_out_and_late_completion_cannot_clear_the_draft` and `cargo test --locked ambiguous_write_timeout_does_not_replay_and_malformed_success_is_uncertain` cover the controlled transport paths. A confirmation is merged by server identity only after a safe post-send catch-up; a refresh that started *before* the send cannot become that catch-up.

## #41 Read older conversations

From `client-gpui/`, start the unchanged rewrite server as in `server-rewrite/README.md` and run `cargo run --locked`. Log in, select a text channel containing over 50 messages with a mix of short and multiline text, and scroll **up** in the conversation to request older pages. The viewport uses a variable-height GPUI `ListState`; the newest page opens at the bottom in chronological display order. A server-issued cursor (never derived from timestamps or IDs by the client) requests each older page. Overlapping IDs appear once, and equal timestamps retain server-defined order. A loading indicator, an explicit **Retry older messages** button after failure, and **Start of conversation** when exhausted distinguish traversal states. Switching channels cancels the selected-channel network request; logout, expiry, server change or rejection invalidates the in-memory history. Requests are bounded by the existing eight-second HTTP timeout. No automatic retry or background reading of unselected channels occurs.

## #40 Create a text channel

Start the unchanged `server-rewrite` (see its README), then run `cargo run --locked` from `client-gpui/` and log in or sign up. In the left pane, enter a name under **Channel name** and select **Create text channel**. The server trims surrounding whitespace; names after trimming must be 1–64 bytes of ASCII letters, digits, spaces, hyphens or underscores. Names are unique ignoring ASCII letter case. Duplicate/invalid names display feedback without clearing the field; a pending write disables another submission and does not navigate. On confirmed creation the returned channel is inserted in server list order, selected, and its newest conversation loaded. An uncertain failure keeps the name and warns that the write may have succeeded: check the channel list before deliberately trying again (no automatic replay). Logout, expiry or server change prevents late responses from navigating. Requests use the existing eight-second HTTP timeout, no redirects, and memory-only session.

Run `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked`, and `cargo build --locked` from `client-gpui/`. Headless tests exercise actual Kit creation controls and selection; targeted HTTP tests exercise the public adapter against unchanged rewrite routes (normalized name, duplicate, invalid name, bearer rejection, decoded response). ## #37 Login/logout slice (historical, before #44 saved sessions)

This client starter now has real login/logout controls. Sessions are **memory-only**: closing the app requires logging in again. No password, token, or message data is persisted by the client. The authenticated shell shows the user and server; the #38 reading slice below adds channels and messages.

Start `server-rewrite` following its README, create a user through its `/api/v1/auth/signup` endpoint (or the #39 signup form above), then from `client-gpui/` run `cargo run --locked`. The login form defaults to `http://127.0.0.1:8081`; change this to the rewrite server's base URL if needed. Enter the existing user's username and password and select **Log in**. The button is disabled while the login request is pending. Select **Log out** to immediately leave the authenticated shell. A failed server revocation leaves you logged out locally and shows a warning; a 401 means the token was already invalid and does **not** confirm a fresh revocation. A known expiry also returns to login. Invalid credentials remain editable for retry.

Only HTTPS is permitted for remote servers; HTTP is limited to localhost or loopback IPs. Certificates are checked normally. Redirects are never followed, so passwords and tokens are not forwarded by a redirect. Login and logout have eight-second request timeouts and run off the UI thread. No automatic request retries occur. Do not use loopback HTTP over untrusted networks.

From `client-gpui/` run `cargo build --locked`, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, and `cargo test --locked`. Tests cover controlled session outcomes/time, loopback TCP boundary fixtures (including redirects/timeouts), and a live HTTP contract test: `http::tests::rewrite_routes_signup_login_logout_and_errors` starts the **unchanged** `server-rewrite` `hamlet::routes` on a disposable port with a temporary SQLite database via `hamlet::connect_to_database`. It checks signup/bootstrap, decoded login and errors via public `AuthApi`, real malformed-JSON 400, bearer logout, protected `/me` 401 after logout, and distinct already-invalid 401. The AuthApi always emits valid JSON, so the malformed-JSON request uses raw HTTP separately. Headless GPUI tests operate real Kit inputs/buttons and verify validation feedback, the flag passed to Kit's disabled button, and inert repeated clicks (Kit's test snapshot does not expose the native disabled flag); the history-selection and variable-height scroll tests remain feasibility probes rather than a production conversation view. For this #37 slice on this machine, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked` (14/14 tests, including the live route test), and `cargo build --locked` succeeded. Native screen-reader, IME, clipboard and desktop interaction need manual verification; headless tests do not establish these integrations.
